ORT WebGPU:
runtime, generation & execution

A design for a predictable, memory-aware and concurrency-safe WebGPU inference stack—grounded in the current ONNX Runtime and ONNX Runtime GenAI implementations.

Status proposed architecture Audited 2026-08-12 ORT dfb403d948 GenAI d2606bba5c Audience runtime, EP & GenAI engineers

Executive summary

There are two architectural boundaries to keep distinct. In ORT core, an InferenceSession owns the loaded/optimized graph, its SessionState, provider instances, allocators, kernels and initializer residency. In GenAI, a Model owns one or more ORT sessions while each Generator owns mutable conversation state: search, KV cache, positions, logits, run options and a capture ID. This sharing is efficient, but the underlying WebGPU session is not a cheap, independent execution context.

01Observed

Session is the executable

ORT loads, optimizes, partitions and materializes kernels per session. WebGPU is one EP in that execution plan, with CPU fallback where allowed.

02Observed

Generator owns state

GenAI generators share the model session but hold independent KV/search state and graph annotation IDs. A generator is stateful and not thread-safe.

03Observed

Capture binds addresses

WebGPU capture retains pipelines, bind groups and dispatch metadata. Reuse requires stable buffer handles, compatible shapes and explicit graph lifetime.

04Decision

One device lane

All work sharing a WebGpuContext must pass through a context-owned submission lane until every mutable runtime component is made re-entrant.

The most important gap. ORT serializes the normal graph-execution branch on one WebGPU session because the EP returns ConcurrentRunSupported() == false. The already-captured replay branch returns through ReplayGraph() before that lock is acquired, and different sessions sharing context ID 0 have no common session lock at all. Both paths can therefore reach the same mutable command encoder, deferred-dispatch window, program map, profiling state and queue concurrently. Capture replay and cross-session parallel execution are not safe boundaries today.S6

Design position

Preserve ORT’s session contract and broad ONNX compatibility, but introduce explicit internal layers: a device runtime, immutable compiled-model artifacts, cheap execution contexts, per-generator state, and an engine scheduler. Make resource scope visible; make capture a capacity-checked contract; and make concurrency a device-runtime property rather than an accidental consequence of session locks.

Configuration has three scopes

Device/context

Physical runtime

deviceId, external instance/device, backend, power preference, validation, buffer-cache modes, binding limit and pending-dispatch window. These configure the shared context and must agree for all users of a context ID.

Session/EP

Executable policy

Preferred layout, graph capture, graph buffer-pool generations, int64, rotary/KV options, forced CPU nodes and PIX. These live on the WebGPU EP instance.

Run/generator

Invocation state

Feeds/fetches, profiling, cancellation, synchronization and gpu_graph_id. GenAI chooses -1 for eager execution or a stable ID for decode replay.

The implementation already distinguishes context and EP parsing, but the public option surface does not strongly enforce scope. The target design attaches a configuration fingerprint to each context and rejects incompatible re-use with an actionable diagnostic.

ORT session

An ORT session is more than a model handle. It is the fully prepared executable. The core lifecycle is deliberately front-loaded so Run() can work from a resolved graph and materialized session state.

1 · LoadParse ONNX/ORT model, external data and metadata.
2 · TransformInline functions, L0/L1 optimizations and layout work.
3 · PartitionQuery EP capability; assign/fuse nodes; insert copies.
4 · FinalizeCreate kernels, upload/prepack initializers, plan memory.
5 · RunValidate feeds, prepare copies, execute nodes, flush EPs.

The actual transform order is explicit: AOT function inlining; required QDQ normalization; level-1 transforms; provider partitioning; higher-level transforms; casts; then copy nodes. WebGPU capability is primarily kernel-registry driven, with special constraints and CPU-preferred-node analysis. Graph capture adds stricter partition validation: no control flow, and only WebGPU compute plus CPU shape work without memcpy nodes.S2S3

Run path

Choose replay or normal execution. ORT reads gpu_graph_id. A captured ID bypasses feed validation, node execution and EP run callbacks, calling ReplayGraph() directly.
Serialize normal execution when required. If any registered EP rejects concurrent run, ORT holds the session mutex around the normal graph-execution branch. The captured replay fast path currently occurs before this lock.
Notify providers. OnRunStart establishes validation/profiling/capture state. Kernels run through the executor.
Flush and finalize. OnRunEnd submits WebGPU work, closes capture, gathers profiling and resets routing.
Retry capture if necessary. ORT can perform up to eight internal runs until an EP reports that the graph is captured. WebGPU currently captures on the first eligible run.
Fallback is a semantic and performance choice. In ordinary execution, unsupported nodes may run on CPU and ORT inserts transfers. In capture mode, WebGPU’s ALLOW_CPU_FOR_SHAPES policy only tolerates CPU shape subgraphs when no copy nodes remain. A capture-enabled model should fail at initialization rather than silently become a hybrid graph whose transfers cannot be replayed safely.

WebGPU EP programming model

The programming model has two layers. The application layer decides which session and generator owns a run and whether that run is eager, capture or replay. The kernel layer turns the selected ORT execution plan into WebGPU Programs and dispatches. Keeping these layers distinct is essential: graph capture changes execution and buffer lifetime, while multiple generators and sessions change ownership; neither implies parallel execution.

Multiple generators and multiple sessions

  • Many generators, one Model/session: each generator owns independent mutable generation state and, with capture enabled, an independent graph ID and static buffers. Their steps may be interleaved sequentially. A single Generator must have one logical owner.
  • Parallel calls on generators sharing one session: ordinary runs are serialized because WebGPU declares ConcurrentRunSupported() == false. Captured replays currently bypass that serialization, so parallel replay is not a supported-safe usage pattern.
  • Many sessions, one context: each session owns its EP and captured graphs, but sessions with the same contextId share the context’s encoder, dispatch queues, caches and profiling/capture state. Their separate session locks do not provide cross-session exclusion.
  • Practical current contract: allow many sessions and generators as independently owned logical objects, but funnel every WebGPU operation sharing a context through one application execution lane. This includes eager Run, initial capture, replay, copies, profiling and graph release.

Kernel and Program layer

A WebGPU kernel is the ORT operator boundary; a Program is one GPU dispatch. One kernel may assemble several Programs. ComputeContext exposes ORT inputs/outputs and temporary tensors, while Program<T> declares tensor bindings, metadata dependencies, uniforms/constants, workgroup size, direct or indirect dispatch, and WGSL generation.S4

// Representative shape of a kernel implementation (illustrative)
FooProgram program{"Foo"};
program.CacheHint(tile_m, tile_n, use_subgroups)
       .AddInput(ProgramInput{x, ProgramTensorMetadataDependency::TypeAndRank})
       .AddOutput(ProgramOutput{y, ProgramTensorMetadataDependency::TypeAndShape})
       .AddUniformVariables({alpha, logical_size})
       .SetWorkgroupSize(64)
       .SetDispatchGroupSize(CeilDiv(logical_size, 64));
return context.RunProgram(program);

Compilation and dispatch pipeline

Describe specialization. The cache key includes program name, explicit cache hint, workgroup/dispatch dimensionality, uniform lengths, buffer segmentation, and only the tensor type/rank/shape dependencies declared by the program.
Build on a miss. The ProgramManager generates WGSL, a bind-group layout and a compute pipeline. Pipeline creation is asynchronous and duplicate keys in the same deferred window share one pending build.
Bind now, encode later. Inputs, outputs and a packed uniform buffer form a bind group. The dispatch record is queued in a bounded deferred window.
Resolve the whole window. Before encoding, all pipeline builds are completed. This prevents a failed shader build from leaving a partially encoded run.
Encode and submit. Direct or indirect workgroups are recorded in order. A flush finishes one WebGPU command buffer and submits it to the device queue.

What is shared

The ProgramManager is owned by WebGpuContext, so pipeline artifacts can be reused across sessions using the same context when their keys match. This is useful shared compilation infrastructure, not shared model weights.

What specializes

Programs opt into exactly the metadata affecting generated WGSL. Over-declaring shape dependency explodes the cache; under-declaring it reuses an incompatible pipeline. CacheHint carries algorithm and device decisions not inferable from tensors.

Hardware-aware paths

The current source includes subgroup FlashAttention, split/reduce decode, subgroup-matrix GEMM/MatMul and N-bit variants, adapter-aware tiling, large-buffer segmentation, f16, optional int64, and 4-bit TurboQuant KV paths. Experimental WebGPU/Dawn features are checked at runtime and must retain portable fallbacks.S12

Simplified whole application using current ORT GenAI C++ API

The model directory contains the GenAI configuration and model files. This example assumes that the WebGPU EP is built in or registered by the host. Change only kCapture to compare capture-off and capture-on behavior.

#include "ort_genai.h"
#include <iostream>
#include <memory>
#include <string>
#include <utility>

// One conversation owns all mutable per-request objects.
struct Conversation {
  std::unique_ptr<OgaGeneratorParams> params;
  std::unique_ptr<OgaGenerator> generator;
  std::unique_ptr<OgaTokenizerStream> output_stream;
  std::string name;
};

Conversation StartConversation(
    OgaModel& model,
    OgaTokenizer& tokenizer,
    const char* name,
    const char* prompt) {
  // GENERATOR PARAMS: per-conversation search policy. Capture policy is inherited
  // from the WebGPU provider option used to construct the Model/session.
  auto params = OgaGeneratorParams::Create(model);
  params->SetSearchOption("max_length", 256);
  params->SetSearchOptionBool("do_sample", false);

  // GENERATOR: mutable tokens/search/KV/position/logit/graph state.
  auto generator = OgaGenerator::Create(model, *params);

  auto prompt_tokens = OgaSequences::Create();
  tokenizer.Encode(prompt, *prompt_tokens);

  // PREFILL: multi-token input. With capture enabled, GenAI still selects the
  // eager path (gpu_graph_id = -1) for this Run.
  generator->AppendTokenSequences(*prompt_tokens);

  return Conversation{
      std::move(params),
      std::move(generator),
      OgaTokenizerStream::Create(tokenizer),
      name};
}

bool Step(Conversation& conversation) {
  if (conversation.generator->IsDone()) return false;

  // DECODE:
  //   capture off -> ordinary ORT Run every time
  //   capture on  -> first eligible one-token step captures; later steps replay
  conversation.generator->GenerateNextToken();

  const auto token = conversation.generator->GetNextTokens()[0];
  std::cout << conversation.name << ": "
            << conversation.output_stream->Decode(token) << std::flush;
  return true;
}

int main(int argc, char** argv) {
  const char* model_directory = argc > 1 ? argv[1] : "./model";
  constexpr bool kCapture = true;  // false = graph capture disabled

  // APPLICATION CONFIGURATION
  auto config = OgaConfig::Create(model_directory);
  config->ClearProviders();
  config->AppendProvider("WebGPU");                         // EP
  config->SetProviderOption("WebGPU", "deviceId", "0");  // CONTEXT
  config->SetProviderOption(
      "WebGPU", "enableGraphCapture", kCapture ? "1" : "0");

  // MODEL: constructing it creates the internal optimized ORT decoder Session,
  // registers a WebGPU EP in that Session, and resolves context ID 0.
  auto model = OgaModel::Create(*config);
  auto tokenizer = OgaTokenizer::Create(*model);

  // MANY GENERATORS may share one Model and its Session. Each owns independent
  // conversation state and (when enabled) a distinct captured-graph ID/buffers.
  auto alice = StartConversation(
      *model, *tokenizer, "alice", "Explain graph capture briefly.");
  auto bob = StartConversation(
      *model, *tokenizer, "bob", "Explain WebGPU buffers briefly.");

  // CURRENT SAFE SCHEDULING MODEL: interleave generators, but do not call them
  // concurrently. Both eventually call the same decoder Session/context.
  while (!alice.generator->IsDone() || !bob.generator->IsDone()) {
    Step(alice);
    Step(bob);
  }

  std::cout << '\n';
  return 0;
}
Why the loop is sequential: the sample demonstrates multiple Generators, not concurrent Run. Each Generator is single-owner. Ordinary Runs sharing the Session are serialized today; captured replay bypasses that session lock, and sessions sharing context ID 0 still share mutable context state. Use a single application execution lane until the concurrent-run design is implemented.

Raw ORT view: Session, EP, context and capture are explicit

GenAI normally constructs these objects internally. The following condensed fragment mirrors the current ORT WebGPU graph-capture test. EP-device registration and error handling are omitted, but the Session, provider options, stable GPU bindings and per-Run graph annotation are concrete current APIs.

// webgpu_ep_device comes from WebGPU plugin-EP registration.
Ort::SessionOptions session_options;
std::unordered_map<std::string, std::string> webgpu_options{
    {"deviceId", "0"},            // WebGpuContext ID; shared by matching sessions
    {"enableGraphCapture", "1"}  // use "0" to disable capture
};
session_options.AppendExecutionProvider_V2(
    env, {webgpu_ep_device}, webgpu_options);               // WebGPU EP

Ort::Session session(env, ORT_TSTR("decoder.onnx"), session_options);

// Capture requires stable GPU buffer handles. Allocate once and bind once.
auto gpu_memory_info = webgpu_ep_device.GetMemoryInfo(OrtDeviceMemoryType_DEFAULT);
auto gpu_allocator = env.GetSharedAllocator(gpu_memory_info);
std::vector<int64_t> shape{3, 2};
Ort::Value input = Ort::Value::CreateTensor<float>(
    gpu_allocator, shape.data(), shape.size());
Ort::Value output = Ort::Value::CreateTensor<float>(
    gpu_allocator, shape.data(), shape.size());

Ort::IoBinding binding(session);
binding.BindInput("X", input);
binding.BindOutput("Y", output);

Ort::MemoryInfo cpu_memory =
    Ort::MemoryInfo::CreateCpu(OrtDeviceAllocator, OrtMemTypeCPU);
auto upload = [&](std::initializer_list<float> values) {
  std::vector<float> cpu_values(values);
  Ort::Value cpu_tensor = Ort::Value::CreateTensor<float>(
      cpu_memory, cpu_values.data(), cpu_values.size(), shape.data(), shape.size());
  Ort::ThrowOnError(env.CopyTensor(cpu_tensor, input, nullptr));
};

Ort::RunOptions run_options;
run_options.AddConfigEntry("gpu_graph_id", "7"); // graph namespace is this Session

upload({1, 2, 3, 4, 5, 6});                      // CPU → existing GPU buffer
binding.SynchronizeInputs();
session.Run(run_options, binding);                // first ID 7 Run: capture

upload({2, 3, 4, 5, 6, 7});                      // same WGPUBuffer handle
binding.SynchronizeInputs();
session.Run(run_options, binding);                // same ID: replay retained bindings

// To force ordinary execution in a capture-enabled Session:
run_options.AddConfigEntry("gpu_graph_id", "-1");
session.Run(run_options, binding);

Capture disabled

The application may supply new compatible tensor objects on each Run. ORT validates feeds/fetches, executes the plan, builds bind groups for that Run and submits through the EP/context.

Capture enabled

A graph ID selects a retained binding set. Update the contents of the same allocated buffers. Replacing input/output objects and reusing ID 7 does not retarget the captured bind groups.

Continuous-batching engine

The new Engine is the better serving boundary. It separates scheduling, cache management and model execution; packs variable-length tokens across requests; and shares a paged KV pool. Dynamic scheduling marks capture eligible only when every selected request contributes exactly one decode token. Graph IDs are derived from batch size and a power-of-two block-table width, reducing the number of captured shapes.S10

Scheduler

Admits requests, reaps completed work, selects a capacity-fitting batch, calculates packed offsets and emits a transactional StepPlan.

Paged cache

Preallocates per-layer block pools, reserves blocks transactionally, emits padded block tables and shares the cache across requests.

Model executor

Builds varlen decoder IO, selects a capture bucket, runs the shared decoder session, then attaches decoder state for batched sampling.

Concurrency vocabulary matters. “Continuous batching” means multiple logical requests advance in one serialized engine step. It does not mean Engine::Step, AddRequest or a Generator can be called concurrently from arbitrary threads.

Buffer management

ORT represents a WebGPU allocation as a WGPUBuffer handle carried through the tensor’s data pointer field; it is not CPU-addressable memory. The allocator asks its current BufferManager on every allocation/free, allowing the EP to route ordinary runs to the context manager and captured runs to a per-graph manager.S5

Captured-graph buffer recycling

Each graph annotation gets an isolated storage/uniform manager. When GenAI destroys the generator, SessionReleaseCapturedGraph releases retained bind groups and donates cached buffers into the EP’s bounded SessionBufferPool. A later generator on the same session can seed its graph manager from the newest pool generation. The pool implementation assumes Run and release are serialized and relies on queue ordering rather than a per-buffer fence. Because captured replay currently bypasses the session Run lock, that assumption is not sufficient under concurrent replay/release and must be fixed before such concurrency is supported.

dense KV bytes ≈ 2 × layers × batch_beam × kv_heads × head_dim × capacity_tokens × bytes_per_element paged KV bytes = 2 × layers × blocks × block_size × kv_heads × head_dim × bytes_per_element capture residency = stable IO + KV + captured intermediates/uniforms + bind groups × shape buckets

Target memory policy

  • Tag every allocation with device, compiled-model, session, generator, graph, step lifetime and an owner ID.
  • Maintain hard and soft device budgets. Hard-limit admission; soft-limit triggers cache trimming and generator eviction.
  • Evict in order: completed step temporaries → unused pipeline variants → retired graph buffers → idle generator KV → model weights only when unloading the model.
  • Do not count bucket capacity as requested tensor size; expose requested, committed and resident bytes separately.
  • Use persistent buffers with capacity views for capture; shapes may shrink within capacity, handles must not move.
  • Keep readback explicit. A D→H copy flushes, stages, maps and waits; it is a synchronization point, not an innocent memcpy.

Graph capture and replay

WebGPU “graph capture” is an ORT-managed replay facility. The EP does not retain a finished WebGPU command buffer. It retains replay-ready dispatch records containing the compute pipeline, bind group, direct/indirect workgroup information and optional profiling metadata; replay re-encodes those dispatches into a new command buffer.S7

Capture contract

Must remain invariant

  • All captured buffer handles and bind-group layouts.
  • Program specialization and pipeline key.
  • Direct dispatch grids, unless indirect dispatch is used.
  • Any uniform value baked into the retained uniform buffer.
  • Tensor capacities and alias relationships.

May change safely

  • Data written into stable input/KV/output buffers.
  • Values read by shaders from storage/uniform buffers when those buffers are deliberately updated.
  • Indirect workgroup counts stored in the captured indirect buffer.
  • Logical views whose byte range stays within the captured capacity.

GenAI supplies a random positive graph ID per legacy generator and releases it in State::~State. Decode tensors use static allocations and shared past/present KV is mandatory, preventing addresses from changing. The Engine instead derives deterministic IDs from batch size and bucketed block-table width, and owns oversized graph buffers for repeated shapes.

PagedAttention capture is not complete on WebGPU. The newly landed v1 path performs a blocking metadata readback per PagedAttention node to derive maximum Q/KV lengths, direct dispatch grids and scratch sizes. Those host-derived values would be frozen during capture. The documented Phase 2 fix is to pass bounded attention_metadata, build sequence metadata on GPU, allocate persistent capacity-sized scratch, and switch all affected Programs to indirect dispatch.S13

  • A replay request that exceeds any capacity is routed to eager execution or a larger bucket; never truncate or reuse optimistically.
  • Graph IDs become internal handles mapped from GraphSignature, avoiding random-ID collision and making diagnostics reproducible.
  • Capture metadata records resident bytes, last use, replay count and invalidation reason.
  • Profiling capture and ordinary capture must not share records if profiling changes query/buffer bindings.
  • The first eligible run currently executes once for capture and once for immediate replay; surface this warm-up cost in telemetry and benchmarks.

Thread safety must be stated per object and per phase. A thread-safe ORT call does not make the caller’s Generator state safe, and a per-session mutex does not protect the process-wide default WebGPU context.

Recommended execution model

Thread-safe without pretending the GPU queue is parallel
Caller threadsSubmit immutable run/request descriptions; never touch device runtime state.
Ingress queuesMPSC queues for generator jobs, engine requests, cancellation and release.
Context laneOrders preparation, allocation routing, encoding, capture mutation and submit.
WebGPU queueProvides GPU timeline ordering; completion tokens retire resources.
  1. Phase 1: add a context-wide non-recursive execution mutex/lane covering OnRunStart → Run → OnRunEnd, replay, copies and captured-graph release across all sessions.
  2. Phase 2: split per-run mutable state (CommandEncoder, deferred dispatches, profiling batch) from shared caches. Permit parallel CPU/WGSL preparation; lock ProgramManager insertion and buffer-cache mutation.
  3. Phase 3: allow multiple recording contexts that submit to the same queue, with explicit resource dependency tokens. Keep graph mutation and eviction serialized.

Lock order is device/context → compiled model → session → generator/graph. Never wait for a GPU completion while holding a higher-level model or generator lock; use a completion token and retire resources on the context lane.

The current implementation supports eager execution, graph capture, multiple generators and multiple sessions, but those features do not yet compose into unrestricted concurrent execution. Target ORT WebGPU architecture

The target is evolutionary: no new public abstraction is required to make today’s C/C++ session API correct. Internally, however, ownership should become explicit so native, web, legacy Generator and Engine paths can share the same runtime safely.

Normative decisions

D1

ORT remains the graph authority

Optimization, partitioning, fallback, operator schemas and session ABI stay in ORT. GenAI supplies LLM state and scheduling, not a parallel graph runtime.

D2

Device runtime owns safety

Any two sessions with the same context ID share one scheduling and synchronization domain. No reliance on unrelated session mutexes.

D3

Immutable artifacts are shareable

Pipelines, optimized plans and read-only initializer allocations may be shared by a verified key; mutable intermediates, bind groups and KV never are.

D4

Generator is single-owner

Generation methods are ordered operations on one state machine. Cross-thread use goes through an executor/queue rather than ad hoc internal locks.

D5

Capture is capacity-based

Every capture declares binding schema and maximum capacities. Indirect dispatch carries dynamic counts; exceeding capacity selects another bucket.

D6

Compilation policy is hybrid

lazy remains universal; warmup compiles a manifest; eager is allowed only when the specialization set is finite.

D7

Memory is budgeted

Device resident bytes are charged to model, generator, graph and cache owners. Admission and eviction use the same accounting.

D8

Async is first-class

A future/promise run surface prevents browser main-thread stalls and allows CPU preparation to overlap submitted GPU work without weakening ordering.

Program-cache sharing key

The current shader key is necessary but not sufficient for persistence or cross-model sharing. The target key adds ORT/EP build ID, Dawn/backend version, adapter/vendor/architecture, enabled features/toggles, limit fingerprint, shader generator version and validation/robustness mode. Cache entries with different fingerprints never alias.

Observability requirements

  • Per Run: queue wait, pipeline-build wait, encode, submit, readback wait, CPU/GPU duration and replay/eager reason.
  • Per cache: hit/miss/build-in-flight, resident bytes, retained-but-free bytes, eviction and key cardinality.
  • Per generator: TTFT, inter-token latency distribution, KV bytes, capture warm-up, capture hits and recaptures.
  • Every forced synchronization has a named reason and call site.

Benchmark rules

Report cold load, first prefill, first decode/capture and steady decode separately. Fix model bytes, quantization, prompt/output length, sampling, adapter, power mode, validation, buffer-cache config and synchronization. Measure CPU wall time and calibrated GPU timestamps; never compare a synchronized path with an asynchronously submitted path as if they were the same latency.

Open questions

Can immutable initializers truly be shared across ORT sessions?

The current context-level initializer BufferManager shares allocation infrastructure, not content identity. A compiled-model cache needs content-addressed initializer ownership, model-package lifetime rules, external-data/mmap semantics and safe teardown before claiming weight deduplication.

Should capture retain bind groups or binding recipes?

Bind groups make replay cheap but freeze buffer handles. Binding recipes enable cheap execution contexts and eviction/restore but add per-replay creation or a second cache. The likely answer is both: immutable bind-group templates plus per-generator instantiated sets.

Where should sampling run for WebGPU?

Today GenAI selects CPU scoring for WebGPU, introducing logits readback. A device sampling path can remove bandwidth and synchronization, but must preserve deterministic seeded sampling, constrained decoding integration and efficient streaming of only selected tokens.

How much parallel recording is useful?

A single WebGPU queue already orders submissions. Parallel CPU preparation may help large dynamic graphs or many sessions, but uncontrolled recording can increase pipeline contention and memory pressure. Instrument the serialized lane first, then split only measured bottlenecks.

Is Engine the long-term generation API?

Use Generator for simple single-request compatibility; use Engine as the serving primitive. They should share GeneratorContext, cache implementations and capture policy rather than grow independent memory and execution stacks.
