Parallel models and generators on ORT WebGPU

A correctness-first design for multiple Models running in parallel, with thread-neutral Session handoff, Session construction overlapping active Runs, concurrently callable Sessions and multiple independent Generators per Session, covering eager execution, graph capture, buffer pools and legacy or paged KV cache.

Design choices

Session ownership

Model is a Session-owned resource category

Every Session owns one private model-resource set: optimized model metadata, initializers, GPU weights, packed weights and other model-specialized allocations. Model resource identity is scoped by Session identity.

No deduplication

Same source, separate resources

If two Sessions load the same model source, each Session creates and accounts for its own model resources. No weights, initializer buffers, packed weights, optimized plans or model-specialized artifacts are shared across those Sessions.

Generator multiplicity

Multiple active Generators

One Session supports multiple simultaneously active Generators. Each retains independent token/search state, stop conditions, KV ownership and graph policy; each Generator remains ordered with at most one of its own steps in flight.

Resulting ownership boundary: the WebGPU device runtime may still share device-generic infrastructure—queue coordination, completion epochs, generic ProgramCache entries and GPU-retired raw buffers—but it never treats Session model resources as a cross-Session cache. Destroying a Session retires its complete model-resource set, after which only raw completed storage may return to the device pool.

Required destruction order

Stop ingress. Stop creating Generators/requests and prevent the Engine or Session from admitting new work.
Drain or cancel work. Remove Engine requests as required and let submitted GPU work reach a completion/retirement boundary.
Destroy request-scoped objects. Destroy Generators, Engine requests and Generator parameters after their use ends.
Destroy the Engine. The Engine must end before the Model that it references.
Release graphs and Sessions, then the Model API object. Explicitly release captured graphs when early memory reclamation is wanted; otherwise Session destruction handles them. Destroy each Session so its private model-resource set retires, then destroy the application-facing Model container.
Shut down globals last. Call OgaShutdown() only after no GenAI object or device-memory holder remains.
API lifetime is not GPU lifetime: public destruction must prevent new access immediately, but buffer reuse and physical destruction remain completion-epoch deferred. An API that merely deletes a C++ object is insufficient for in-flight WebGPU work.

Executive summary

01Required

Per-run state

Move encoder, deferred commands, profiling, allocation routing and capture recorder out of shared context/EP fields into one explicit WebGpuRunContext per invocation.

02Required

Device-wide scheduler

All Sessions sharing a context use one admission, submission, completion-epoch and memory-budget domain with per-Session fairness.

03Required

Two pool paths

Eager Runs lease transient arenas; graph replay leases address-stable slots. Neither path may expose a buffer for reuse before its GPU completion epoch.

04Required

KV is state, not scratch

Each legacy Generator owns exclusive KV, while paged KV uses transactional block reservations and per-in-flight metadata slots.

Target product contract: A fully initialized Session may be handed from its creation thread to another thread, and a new Session may be constructed while an existing Session has a Run in flight. Models, Sessions and different Generators may otherwise have overlapping calls. A single Generator remains an ordered state machine and has at most one generation step in flight. Parallel work is bounded by device memory and graph/KV slots, and is submitted through one ordered device-runtime domain; this is safe concurrency, not a promise of simultaneous GPU kernels.

The final call to ConcurrentRunSupported() should change to true only after eager Run, capture, replay, copies, profiling, graph release, buffer reuse and device loss pass the same concurrency gates. Enabling the flag earlier merely removes the session mutex; it does not create isolation.S1S2

Concurrency contract

Thread safety must be defined for an object and an operation. The proposed contract separates logical multiplicity, overlapping host calls, parallel command recording and GPU overlap.

Normative rules

C1

Generator is single-owner

One Generator is an ordered mutable state machine. Its methods must not overlap. Different Generators may progress concurrently through a scheduler.

C2

Run bindings are exclusive while in flight

Writable inputs, outputs, temporaries, KV and captured slots cannot be mutated or reused until their completion token retires.

C3

Session is concurrently callable

Independent Runs on one initialized session may overlap after the per-run split. Initialization, option mutation and teardown remain exclusive.

C4

Context owns ordering

All queue writes, command submissions, readbacks and resource retirement receive a monotonically ordered context epoch.

C5

Captured graph is immutable

Ready graph commands, pipelines, bind groups and capacity signature never mutate. Recapture constructs a replacement and swaps it atomically.

C6

Session model resources are read-only after publish

Each Session privately owns its optimized plans, initializers, prepack data and model-specialized artifacts. Runs in that Session may read them after publication; another Session never references them.

C7

Destruction is deferred

Session, graph and buffer API lifetime may end before GPU lifetime; actual resource release occurs only after the final referencing epoch completes.

C8

Concurrency is bounded

Admission accounts for buffers, graph slots, pending compilation, command buffers and readback staging. Overload waits, batches or rejects predictably.

C9

KV reservation is transactional

Contiguous slots or paged blocks and metadata are reserved before recording, committed after successful completion and never reassigned before retirement.

C10

Sessions have quotas

Every model-resource allocation and admitted Run is charged to exactly one Session. Device scheduling provides weighted progress and prevents one Session from consuming all shared capacity.

C11

Ready Sessions are thread-neutral

After synchronized publication, a Session is not affine to its construction thread. Construction is private until initialization succeeds; device-facing initialization participates in the same admission, submission and completion protocol as Run.

Target topology: device × Sessions × Generators

The unit of application parallelism is a different Generator, not two overlapping calls on one Generator. The unit of ORT execution isolation is a RunContext. A Model is represented inside this hierarchy as a private Session-owned resource set, not as a cross-Session sharing layer. All work that resolves to the same contextId shares one device runtime, allocator budget and ordered submission timeline—even when different Sessions load the same model source.

Current implementation: why the flag cannot simply change

Today WebGPU returns false from ConcurrentRunSupported(). ORT consequently locks session_mutex_ around ordinary graph execution. The already-captured replay fast path is earlier in InferenceSession::Run and calls ReplayGraph() before that lock. Different sessions have different mutexes and therefore never coordinate a shared context.S1S2

Exact API and lifetime contract

Handoff

Construction thread → Run thread

The constructor and Initialize() must finish successfully before the Session is published. Transfer the owning handle through thread start, a mutex/condition variable, future/promise, channel, or another release/acquire mechanism. A raw pointer written and read without synchronization is still a caller data race.

In flight

Run owns a strong lease

Admission creates a strong Session/runtime lease held until the completion epoch and callbacks retire. Dropping the application’s last Session handle stops new admission but cannot free EP, graph, initializer or device resources referenced by A’s Run.

Private build

Session B is not observable

B transitions through Allocated → CpuPreparing → DeviceInitializing → Publishing → Ready. No Run, Generator or graph lookup may observe B before Ready. Failure transitions to Retiring and destroys submitted resources only after their last epoch.

Immutable ready state

No concurrent mutation

After Ready, the optimized graph, execution plan, provider configuration, initializer table and allocator-domain identity are frozen. Session options, external-initializer registration and provider replacement do not overlap Run.

Interaction with graph capture, buffers and scheduling

  • Capture off: A’s eager RunArena and B’s immutable-weight/init allocations are different domains. Both return buffers only through epoch retirement.
  • Capture build or replay: B initialization cannot read or mutate A’s graph annotation, builder, instance lease, allocation route or captured buffers. It records no command into A’s graph. Optional B warmup/capture is a separate post-init graph-build task with B’s own slot.
  • Queue operations: direct Queue.WriteBuffer, Submit, copy flushes, readback and error-scope operations must all use the runtime coordinator. Queue thread safety alone does not provide ORT ownership or completion semantics.
  • Latency: classify cold Session initialization as bounded background/bulk work. Chunk large uploads and compilation admission so interactive decode Runs retain progress; do not hold the submission lock during file I/O, graph transforms or pipeline waits.
  • Memory: creation can block or fail before allocation when A’s graph/KV/resident buffers plus B’s estimated initializer/prepack/staging peak exceed the device or Session limit. Session construction must not evict an in-flight graph/KV slot.

Incremental implementation option

The first safe milestone does not need parallel command recording. Route Run A and every device-touching step of Init B through the context task lane; CPU construction still overlaps, while device operations serialize in short tasks. The full design later gives A a WebGpuRunContext and B a WebGpuInitContext, allowing independent recording with ordered submission. In both milestones, thread handoff is supported and Session B creation may begin before A completes.

Current limitation: do not claim this same-context scenario is supported merely because Session A and B have different session_mutex_ objects. Session B’s initializer upload currently reaches the shared context encoder/deferred list and can call Flush(); the factory mutex is no protection once provider/context acquisition returns.S20

Illustrative target C++ application

The types ending in Async are proposed internal/target APIs, not claims about the current public surface. Synchronous wrappers use the same scheduler and wait without holding runtime locks.

int main() {
  auto runtime = WebGpuDeviceRuntime::Create({
      .context_id = 0,
      .concurrency = ConcurrencyPolicy::ParallelRecord,
      .max_inflight_runs = 6,
      .memory_budget = 8_GiB,
  });

  // A Ready Session can be acquired by many threads. A shared_future supplies
  // the required release/acquire publication edge.
  std::promise<std::shared_ptr<ExecutionSession>> publish_a;
  std::shared_future<std::shared_ptr<ExecutionSession>> ready_a =
      publish_a.get_future().share();
  std::latch first_a_steps_queued{2};

  // T1: create Session A. This thread does not become A's execution thread.
  std::jthread session_a_builder([&] {
    auto session_a = ExecutionSession::CreateReady(runtime, "model-a.onnx", {
        .graph_capture = GraphCapturePolicy::DecodeCapacityBuckets,
        .max_graph_slots_per_signature = 2,
        .kv = PagedKvPolicy{.block_size = 16,
                            .metadata_slots = 4},
    });
    publish_a.set_value(std::move(session_a));
  });

  auto run_a_generator = [&](GeneratorParams params) {
    auto session_a = ready_a.get();
    auto generator = session_a->CreateGenerator(std::move(params));

    // DecodeOneAsync() snapshots Generator state, reserves disjoint KV blocks,
    // leases one metadata/graph slot, and queues one Session Run.
    auto first_step = generator->DecodeOneAsync();
    first_a_steps_queued.count_down();       // queued, not completed
    first_step.get();

    while (!generator->IsDone()) {
      generator->DecodeOneAsync().get();    // ordered within this Generator
    }
  };

  // T2 and T3 share Session A, but never share a mutable Generator.
  std::jthread generator_a0([&] { run_a_generator(params_a0); });
  std::jthread generator_a1([&] { run_a_generator(params_a1); });

  // T4: begin constructing B while A0 and A1 have Runs in flight.
  std::jthread session_b_and_generator([&] {
    first_a_steps_queued.wait();
    auto session_b = ExecutionSession::CreateReady(runtime, "model-b.onnx", {
        .graph_capture = GraphCapturePolicy::Disabled,
        .kv = ContiguousKvPolicy{.max_state_slots = 2},
    });
    auto generator_b0 = session_b->CreateGenerator(params_b0);
    while (!generator_b0->IsDone()) {
      generator_b0->DecodeOneAsync().get();
    }
  });

  // jthread destructors join. Runtime/Session/Generator destructors stop new
  // admission; GPU-referenced buffers retire only after completion epochs.
}

Migration policy

Serialized device lane

Target policy

Per-Session parallel-Generator contract

  • A Session accepts multiple admitted RunContexts concurrently. It does not expose mutable “current Run”, “current graph” or “active buffer manager” fields.
  • Each Generator registers a stable GeneratorId and monotonically increasing operation number with the Session. Admission rejects or queues operation n+1 until operation n has committed.
  • The Session owns graph and generator-state slot namespaces. A caller never supplies a random graph ID that can collide with another Generator or Session.
  • Graph release, Generator destruction and Session teardown first stop new leases, then defer physical buffer/KV release until all referencing epochs complete.
  • A Session may cap its parallel Generators below the application count. Excess Generators remain logically alive but wait in admission without reserving transient run memory.

Capture and replay rules

  1. Single-flight capture. Only one builder for a signature/slot. Other Runs may wait, use an older Ready instance or execute eagerly according to policy.
  2. Private construction. Capture writes only to the builder’s command list and arena. The instance becomes visible with one atomic publication after pipelines and bindings are complete.
  3. Exclusive writable slot. A GraphInstance lease is held from the first CPU/GPU input update through the completion epoch. It cannot be replayed again until released.
  4. Read-only sharing. Initializers and immutable Program artifacts may be referenced by all instances and Runs.
  5. Stable capacity. Data values and indirect counts may change inside stable buffers. Handles, ranges, layouts, direct grids and specialization-dependent metadata may not.
  6. Deferred release. Removing a generator or evicting a graph prevents new leases; resources retire only after builders, leases and submission epochs finish.
  7. No silent mismatch. A request outside the signature selects a larger slot, recaptures or runs eagerly. It never reuses an approximately compatible graph.
  8. Opaque handles. Replace random integer annotation IDs with {session, signature, slot, generation}. The EP may translate the handle internally, but stale generations and cross-Session use fail before lookup.
  9. Budget before build. Reserve the complete pinned-slot estimate before capture begins. A partially built graph is never published and its buffers enter the retire queue—not the free pool—on failure.
  10. No mutable shared metadata. Block tables, positions, masks, indirect counts, query buffers and upload staging are slot-local for every overlapping replay.

Explicit change checklist: multiple Generators in one Session

This section is normative for the target where different Generators of one initialized Session may have overlapping steps. “Supported” means independent host calls are race-free, buffer/KV/graph ownership is isolated, failures and teardown are defined, and memory is bounded. It still does not promise simultaneous GPU kernel execution.

Acceptance contract: Generator A0 and A1 may call the same Session concurrently. Each has at most one ordered step in flight. They may both read that Session’s immutable model resources but never a writable RunArena, concrete graph slot, contiguous-KV slot, paged block write set, metadata slot or output slot. Buffer-pool design: eager and captured execution

Buffer concurrency is the hardest correctness boundary. WebGPU tensor data pointers carry buffer handles, cache managers use unsynchronized containers, capture pins addresses, and queue completion—not C++ scope—determines when reuse is legal.S7

Hierarchy decision: keep semantic objects—GraphInstances, Generator state slots and KV ownership—inside the Session, but place one raw DeviceBufferPool above all Sessions sharing a WebGPU device runtime. Finishing a Generator returns a complete compatible slot to its Session. Finishing a Session dismantles its semantic objects after GPU retirement and returns only raw buffers to the device pool. Do not introduce a cross-Session graph-instance pool initially.

Replace cache modes with explicit allocation domains

The current Disabled, LazyRelease, Simple, Bucket, Graph and GraphSimple implementations combine size policy, ownership and release timing in mutable containers. Under concurrency, BufferManager should remain the kernel-facing API but route every allocation through an explicit domain carried by WebGpuRunContext.

A large per-Session eager buffer cache is deliberately avoided: it strands capacity when one Session becomes idle while another is active. Graph path: stable GraphArena and retired-arena reuse

Look up a signature and slot. Admission first seeks an Idle compatible GraphInstance. Slot acquisition precedes writes to captured inputs or metadata.
Build atomically on a miss. Reserve the full pinned-byte estimate, acquire buffers into a private GraphArena, create bind groups and capture commands, then publish the complete slot. Failure retires every acquired buffer by its last submitted epoch.
Keep addresses pinned. Captured buffers remain GraphPinned across replays; per-replay Release calls only update arena bookkeeping. The slot lease prevents concurrent overwrite.
Finish a Generator. When a Generator owns the slot for its lifetime, stop its admission and wait for its final dependent epoch. Retire or evict a graph. Unpublish the slot, reject new leases, wait for builder/replay references and completed epoch, then release commands and bind groups. A live Session may keep an address-layout-compatible arena in RetiredGraphArenaPool; otherwise its raw buffers enter DeviceBufferPool.
Drain a Session. Do not preserve concrete GraphInstances across Session destruction. Drain every Session-local ready/retiring arena and return its raw completed buffers to DeviceBufferPool.

Correctness mechanisms

  1. Allocation ownership. Every buffer/range has one owner ID, usage flags, capacity, generation and last-use epoch. Debug builds reject double release and stale generation.
  2. GPU retirement. Release() moves a lease to a retire queue; it never makes the buffer immediately acquirable. Completed queue epochs drain that queue.
  3. Per-run arenas. Writable intermediates cannot come from a session-wide active pool. They are leased to a Run and bulk-retired with it.
  4. Mapped-state discipline. A mapped buffer is never bound or copied by the GPU. Mapping callbacks own the buffer until unmap and completion publication.
  5. Range hazards. Exact buffer plus byte range is tracked for external/preallocated bindings. Overlapping writes are rejected or dependency-ordered.
  6. Capture pinning. Graph buffers never enter the free cache while their instance is Ready or leased. Pool donation occurs only after graph retirement.
  7. OOM atomicity. A Run reserves its expected memory class before recording. Failure releases reservations without partially publishing a graph or generator step.

Pool synchronization and lock scope

  • Shard free lists by PoolKey hash. Acquire/release metadata under one shard lock; never hold it while creating a Dawn buffer, waiting for the queue, compiling a pipeline or calling user code.
  • Use a separate ledger lock (or atomic counters plus a reservation mutex) to reserve device-total and per-Session bytes before allocation. If physical creation fails, roll the reservation back without publishing partial leases.
  • The completion callback only advances completed_epoch and schedules a retire-drain task. Drain tasks take retire/shard locks in a fixed order and never enter Session or Generator state.
  • GraphSlotPool and GeneratorStateSlotPool locks protect only lookup/state transitions. A slot state changes to Leased before its buffers are touched; queue completion changes it through an enqueued continuation.
  • Debug builds maintain a handle/range hazard table. Submission verifies no two unordered RunContexts own overlapping writable ranges, except paged-KV writes proven disjoint by block reservation.

Completion epochs without per-Run blocking

The WebGPU queue is ordered, so the runtime can layer logical epochs on submissions. Assign every submitted batch an increasing epoch and periodically request a queue-completion callback. Completion of epoch N proves that all earlier epochs on that queue are complete; the retirement queue may then expose their buffers to caches. Callbacks should be coalesced rather than created for every tiny decode submission, with forced checkpoints for readback, memory pressure, graph/session teardown and bounded-latency futures. Callback code only advances the completed epoch and enqueues continuations—it never runs user code or mutates session state directly.

Important: a logical submission epoch is not a second GPU queue or hardware fence exposed to callers. It is runtime bookkeeping built on ordered submission and queue-completion notification, used to make C++ resource lifetime match GPU lifetime.

Performance design

Fast allocation path

Use size-class free lists with short shard locks or lock-free single-owner queues. Refill a per-worker/per-run local cache in batches. Do not put one global allocator mutex around every Program buffer.

Budgeted residency

Account requested bytes, actual bucket bytes, pinned graph bytes, in-flight bytes, cached-free bytes and readback/upload bytes separately. Admission uses actual resident estimates.

Eviction order

Excess device-free buffers → Session eager hot caches → idle graph slots/retired arenas → idle Generator/KV state allowed by policy → optional device-generic pipelines. Session model resources remain owned until Session teardown; never evict in-flight, retiring or caller-pinned resources.

Staging and copies

Coalesce small position/mask/token uploads. Use GPU copies for non-zero subranges rather than CPU round trips. Treat download/map as a scheduled synchronization operation.

  2. Bind exclusively. Every RunContext for that Generator holds a strong slot lease. The next step waits on the prior step, so the same KV slot is never written by two overlapping Runs.

  4. Capture fixes capacity. Before first decode capture, allocate the final declared capacity and ensure prefill results reside in those handles. Capacity overflow selects eager fallback or a new state/graph slot; it never mutates the existing capture.

Reservation and commit protocol

Plan under the Session KV authority. The Engine/control loop snapshots committed tables, selects generators, computes target slots and capacity bucket, then atomically reserves all required blocks or admits none.
Lease metadata. Acquire a metadata slot whose batch/column capacity matches. Fill only that slot. Capture-off Runs still require separate metadata when two batches overlap; the current single block_tables_value_ is not sufficient.
Publish an immutable reservation. Workers receive block IDs, byte-range write sets and metadata handles. They do not mutate BlockPool or committed tables.
Submit and mark in flight. Attach the submission epoch to new/tail blocks and metadata. Later steps of the same Generator depend on this completion; independent Generators may use disjoint blocks.
Commit on success. The control loop advances committed token counts and table membership only after successful completion. A reservation cancelled before submission can be released directly; after submission, failure/cancellation moves blocks to Retiring until that epoch completes.
Remove safely. Request cancellation/destruction removes it from scheduling immediately but defers block reuse until every Run that references its table or blocks has retired.
Single logical owner, parallel GPU work: BlockPool does not need fine-grained locks if exactly one Session Engine/control loop performs Plan/Reserve/Commit/Remove. Run workers consume immutable reservations. If direct per-Generator threads bypass that authority, BlockPool and block tables need equivalent transactional synchronization; locking only AvailableBlocks() is insufficient.

Paged KV with graph capture

  • Allocate the physical per-layer K/V tensors once for the Session and keep their handles stable for the lifetime of every graph that binds them.
  • Graph signature includes block size, number of physical blocks, KV heads/head size, dtype/quantization/layout, batch bucket and block-table-column bucket.
  • Each simultaneously in-flight replay leases a different KvMetadataSlot and therefore a different GraphInstance/bind-group set, even though all instances may bind the same physical K/V arena.
  • Block IDs in two reservations must be disjoint for writes. Debug hazard validation translates IDs to layer/range write sets; shared read-only prefix blocks require explicit reference counts and copy-on-write rules before prefix sharing is enabled.
  • Metadata that changes each step must be written inside stable buffers. Dynamic dispatch counts are produced on device and consumed through indirect dispatch.
  • Until WebGPU PagedAttention removes host metadata readback and supports the required indirect path, paged-KV steps remain eager even if the Session has graph capture enabled. The metadata-slot pool is still required for eager overlap.S13

KV correctness invariants

  1. No physical contiguous slot or paged block is writable by two unordered Generator operations.
  2. A block/slot generation changes on reassignment; stale block tables and graph handles fail validation.
  3. Committed logical token length never advances before successful GPU completion, and rollback never exposes in-flight memory to another request.
  4. Metadata capacity covers the selected batch and maximum referenced block ID count; unused entries are deterministically padded.
  5. Graph capture never observes a changed K/V or metadata buffer handle. Eager growth creates a replacement and an ordered copy.
  6. KV accounting reports physical arena bytes, assigned/reserved/free logical blocks, contiguous idle-slot bytes and capture metadata separately.

Scheduling and performance

WebGPU normally exposes one queue. Parallel host recording can reduce queue idle time and pipeline-build stalls, but it does not guarantee simultaneous shader execution. Too much concurrency can increase memory footprint, compilation duplication, cache pressure and tail latency.

Context scheduler responsibilities

Admission

Bound in-flight Runs, bytes, capture builders, compiles and readbacks before work starts.

Fairness

Schedule across Session queues with weights/aging, then by request priority. Prevent one Session or large prefill from starving decode.

Batching

Hold a short configurable window to merge uploads/submissions or form Engine batches when beneficial.

Backpressure

Expose queue delay and deterministic wait/reject behavior instead of unbounded host/GPU queues.

Two-level scheduling

  1. Per-Session readiness. A Session exposes only Runs whose Generator predecessor, graph/metadata slot and KV reservation are ready. It may batch compatible Generators from that Session.
  2. Device admission. The context scheduler selects among ready Session queues using priority plus weighted deficit/aging, checks Session/device byte budgets, then grants a bounded RunContext slot.
  3. Recording. Admitted work may prepare/record on workers. A worker cannot reserve unbounded additional bytes; material estimate growth returns to admission.
  4. Submission. One coordinator establishes queue-write and command-buffer order and assigns epochs. Per-Generator predecessor edges are always honored; unrelated Sessions have no ordering promise beyond their assigned epochs.

Failure domains

  • Run-local validation or shader error: fail the Run and graph builder; other Runs remain healthy unless shared device state is invalid.
  • Pipeline build failure: complete all waiters for that key consistently. Retry only under explicit policy/version change.
  • Submission/validation error: mark affected context epoch failed; conservatively poison the context if execution state cannot be proven coherent.
  • Device loss: transition the DeviceRuntime to Lost, reject admission, fail queued/in-flight futures, invalidate every graph, buffer and pipeline, and require explicit recreation.
  • Callback safety: no exception escapes a Dawn callback. Capture status in heap-owned callback state and complete promises outside internal callback locks.
  • Timeout: a host deadline cancels publication, not submitted GPU work. Metrics distinguish deadline exceeded before and after submit.

Deadlock prevention

  1. Never wait on queue completion, map completion or pipeline future while holding cache, session, graph or scheduler locks.
  2. Completion callbacks enqueue retirement/continuation work; they do not call user code or recursively enter session execution.
  3. Synchronous Run waits only on its future after releasing all runtime locks.
  4. Teardown switches to Draining, prevents new work, then awaits owned futures through the scheduler—not while holding registry locks.

Stress techniques

  • Run under ThreadSanitizer where supported and add deterministic barriers at capture begin/end, cache acquire/release, submit and graph unpublish.
  • Inject random delays into pipeline callbacks, queue completion, readback mapping and graph destruction to expand race windows.
  • Poison retired buffers and validate generation/owner on acquire in debug builds.
  • Repeat thousands of short-lived Generators across shared sessions and contexts with randomized capture eligibility and cancellation.
  • Hold queue completion behind deterministic barriers while destroying Models, Sessions, Generators, graph slots, contiguous KV slots and paged requests; verify nothing returns to a free pool early.
  • Pause Run A after allocation, deferred dispatch, capture begin, encoder creation and submit in separate trials; start Session B initialization on another thread at each barrier and verify B neither drains nor mutates A’s state.
  • Create a Session on one thread, publish it through promise/future, mutex, channel and thread-start edges, then Run on another thread; add a negative debug-only test that rejects use before Ready.
  • Race first-context creation for the same key and different devices; verify per-key single-flight, unrelated-device progress, shared failure delivery and no raw context lifetime gap.
  • Run two Sessions with asymmetric prefill/decode loads and tight per-Session quotas; include both same-source and different-source pairs, then verify weighted progress, resource isolation and deterministic backpressure.
  • Randomize paged block reservation/commit/cancel order and compare block snapshots plus outputs with a single-in-flight reference.
  • Compare every concurrent result against a serialized reference using the same model, inputs and numeric tolerances.

Performance reporting

Report concurrency 1, 2, 4 and 8 only when admitted by memory. Include cold/warm pipeline states, capture off/on, one/many sessions, one/many generators and Engine batching. Required metrics are throughput, TTFT, inter-token P50/P95/P99, queue idle, admission wait, lock wait, compile wait, submissions, dispatches per submission, readback count, peak resident bytes and graph-slot occupancy.

Benchmark rule: a throughput win that comes from extra resident KV/graph memory must report the resulting maximum active-request capacity. Concurrency and capacity trade the same device budget.

Open decisions

Should submission itself be callable from recording workers?

Prefer one logical coordinator that assigns epochs and calls queue submission. It may be lock-based rather than a dedicated thread, but queue writes, submits and retire epochs must have one total order.

How many graph slots should one signature keep?

Default to one for memory efficiency. Add slots adaptively when replay wait is material and the memory budget has headroom; evict idle excess slots first.

Should same-session Runs preserve call order?

Submission order should follow admission sequence within the same priority class unless dependencies or scheduler policy say otherwise. Completion callbacks may execute on different host threads, but result identity is explicit.

Can buffer range hazards be inferred automatically?

ORT can validate known tensor buffer/range pairs. External interop and hidden aliasing may require caller-declared ownership or explicit dependency tokens; otherwise use conservative exclusivity.

When should Engine allow multiple batches in flight?

Only after cache reservations and request transactions have independent commit domains. One batch in flight remains the safe default; dynamic batching often supplies enough queue occupancy.

Should a context use a dedicated scheduler thread?

Not necessarily. A lock-free ingress plus a short-held submission mutex may be cheaper. Choose from measurements, but preserve the same task, ordering and completion semantics.
