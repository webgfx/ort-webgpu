1. Current programming model

Generation context is the design-level container for one Model/internal Session and multiple live Generators. It is distinct from the WebGPU device context, which may be shared by multiple generation contexts. The current OGA C API has no OgaContext handle; the Model, its internal Session and its associated Generators collectively form this boundary.

No deterministic result-correctness defect was identified solely from serialized graph replay when the ID, signature and bindings remain unchanged. The implementation nevertheless has the following correctness and recovery defects. Part 3 gives the corresponding changes.

2. Concurrent programming model

The target supports multiple live Sessions, multiple live Generators inside each Session, concurrent execution of different Generators on different threads, and sequential handoff of one Generator between threads. It does not support overlapping state mutation of the same Generator and does not promise simultaneous GPU kernel execution: one device runtime still orders queue writes and submissions.

Multiple SessionsDifferent Sessions may initialize and Run concurrently, including on the same WebGPU context.
Different Generators on different threadsGenerators in the same or different Sessions may have active steps concurrently because each owns independent mutable state and leases.
Thread-mobile GeneratorSuccessive calls may run on different threads, but one admission guard permits only one active state-mutating call.
Definition — generation step: one invocation of OgaGenerator_GenerateNextToken(generator) for one Generator. It starts when the call passes that Generator's admission guard, may perform one or more internal ORT Session Runs, consumes the current token/KV/search state, and ends when the next token plus the updated Generator state are committed or the call fails without committing. “At most one step in flight” means two threads must not execute this state-mutating interval concurrently on the same Generator. GPU storage used by the step can remain in the retiring state until its completion epoch; this physical retirement period is tracked separately and does not permit early buffer or KV reuse.
Required parallelism: T1 may run Generator A1 while T2 runs Generator A2, even when A1 and A2 share one Session. Their Generator state, KV leases and graph/eager allocation domains are independent; Session registries and device-runtime services provide the required synchronization.
Thread handoff is supported; overlap is not. A Generator has no permanent worker-thread affinity. It may be created on T1, used on T2, and used for its next step on T3 after a release/acquire synchronization edge. This supports worker pools, asynchronous continuations and work stealing. It does not allow T2 and T3 to mutate that Generator simultaneously: step N+1 depends on step N's token, search state, KV cache and graph bindings.

Graph capture and buffer behavior

  • Capture on: the Session owns graph templates and one or more address-stable graph slots. A Generator leases a compatible slot for capture/replay; the slot returns to the Session only after its last replay epoch.
  • Capture off: each Run leases an eager arena for transient tensors, descriptors, staging and queries. The arena descriptor returns Session-locally; raw buffers recycle device-wide after completion.
  • KV cache: KV is persistent Generator state, never general scratch. Contiguous KV leases one Session slot per Generator; paged KV leases blocks transactionally and uses per-in-flight metadata slots.
  • Backpressure: admission may wait or fail when graph slots, KV capacity, metadata slots or the device memory budget are exhausted.

3. Problems and solutions

Current graph capture is already per Generator in logical identity and lifetime. Concurrent execution is not: the WebGPU EP reports that concurrent Run is unsupported, and mutable replay, profiling and allocation state is shared below the Session boundary.

Current graph-capture implementation review · complete issue list

Verified ownership: each GenAI Generator creates its own State. When capture is enabled, State::State creates its graph ID, State::Run writes that ID to gpu_graph_id, and State::~State calls SessionReleaseCapturedGraph. Thus the graph's logical identity follows the Generator. ORT physically stores captured commands and the per-graph BufferManager in Session EP maps keyed by that ID.
Per-Generator graph buffers are necessary, not sufficient. They prevent intentional buffer sharing between Generators, but concurrent threads still touch the Session graph registry, replay/release paths, allocator routing, program cache and shared WebGpuContext recording/profiling state. Different Generators become safe only after those shared layers are synchronized or made per Run.

Eager mode: reuse the graph-capture pattern, not its lifetime

Recommendation: generalize graph capture's allocation-domain routing, but do not permanently attach a graph-style BufferManager to every eager Generator. Use one interface with two lease types: a Generator-lifetime pinned GraphLease, and a completion-bounded EagerLease owned by one Run. This preserves isolation while allowing eager memory to be shared after each step.

Represent the choice in WebGpuRunContext as an AllocationDomain: Graph(generator_graph_lease) or Eager(run_arena_lease). Persistent outputs and KV remain Generator-owned in both modes. Only transient intermediates, uniforms, staging and query buffers use the eager Run lease. On completion they move leased → retiring → free; the Session pool may then hand the arena to any compatible Generator. Raw buffers may ultimately return to the device-wide pool.

Eager-pool concurrency protocol: pool metadata is protected by a short-held mutex or size/usage shard. Acquisition atomically removes one compatible record from free and assigns an exclusive lease ID. Release validates immutable pool provenance plus a generation counter, then moves the record to retiring(completion_epoch); only completion processing may return it to free. Reserve budget under the lock, but create physical buffers, record commands, submit and wait outside it. This prevents duplicate leases, wrong-pool returns, ABA/stale releases and GPU waits under pool locks.

Implementation order

Enforce API admission first. Add thread-independent Generator close/admission, fail-fast busy results, immutable parameter snapshots and explicit reader/cancellation semantics. Different Generators remain independently admissible while unsupported same-Generator overlap is contained.
Isolate Run, transfer and initialization state. Introduce WebGpuRunContext/WebGpuInitContext, transfer contexts and graph/eager AllocationDomain; remove current-Run fields from the EP/device context.

Intentional limitations

  • Different Generators in the same or different Sessions are supported concurrently on different threads; shared Session and device structures must not serialize their entire Runs.
  • A Generator may be handed to a different thread after synchronization, but it has at most one active generation step; methods that mutate the same Generator do not overlap.
  • Generator parameters are immutable after they are bound. Different concurrent requests use separate parameter objects or separate immutable snapshots.
  • Graph replay requires an exact compatible signature and an available graph slot; otherwise the Run waits, falls back to eager when legal, or returns backpressure.
  • Model resources are private to each Session. Sessions loading the same model source do not share weights, initializers, packed weights or graph artifacts.
  • Safe concurrent API calls do not guarantee concurrent GPU kernels. WebGPU queue submission remains ordered.
  • The target is memory-bounded. Maximum active Sessions and Generators depend on model weights, KV capacity, graph slots and the device budget.
  • OgaShutdown is not concurrent with live Models, Generators, Engines, Runs or callbacks; it is a final quiescent operation.
Completion criterion: steps for different Generators demonstrably overlap on different host threads—including two Generators in one Session—and produce the same results as serialized execution, with no data races, early buffer/KV reuse, cross-Run graph state, resource leaks, whole-Run Session serialization or starvation.
